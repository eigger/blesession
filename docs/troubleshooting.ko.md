# 공통 Bluetooth 문제 해결

[English](troubleshooting.md) | **한국어**

이 안내는 해당 통합의 기기별 문제 해결 문서와 함께 사용합니다. 로컬 Bluetooth 어댑터와 ESPHome 프록시를 다루며 blesession을 사용하지 않는 통합에도 적용할 수 있습니다. 안내를 따르기 위해 Python 라이브러리를 설치할 필요는 없습니다. Bluetooth 경로가 아직 준비되지 않았다면 [프록시 설정과 추천 기기](bluetooth.ko.md)부터 확인하세요.

지원 모델, 깨우기 순서, 페어링, 키, 안전한 명령과 재시도 설정은 기기 통합에서 정합니다. 이 안내가 진단 엔티티·자동 재연결·재시도·timeout 설정을 통합에 추가하지는 않습니다. 설치된 통합이 실제 제공하는 정보와 설정만 사용하세요.

## 빠른 확인

1. 실패 시각과 요청한 작업을 기록합니다. 쓰기나 실제 동작 명령을 반복하기 전에 기기가 이미 수행했는지 확인하세요.
2. 정확한 지원 모델·펌웨어, 배터리·전원과 필요한 깨우기·연결 모드를 확인합니다. 잠든 기기가 일시적으로 사용 불가가 되는 것은 예상 동작일 수 있습니다.
3. **발견**과 **연결**을 구분합니다. 광고나 최근 엔티티 값이 보인다고 현재 GATT 연결·읽기·쓰기가 성공한 것은 아닙니다. 광고만 사용하는 기기는 GATT가 필요하지 않을 수도 있습니다.
4. 한 번에 하나의 연결만 허용하는 모델은 휴대폰 앱이나 다른 게이트웨이의 연결을 종료합니다. 필요한 페어링·본딩은 유지하고 일반적인 첫 조치로 초기화·재페어링하지 않습니다.
5. 실제 어댑터·프록시, 전원·네트워크와 같은 경로의 다른 기기도 실패하는지 확인합니다. 프록시 연결은 GATT 지원(`bluetooth_proxy.active: true`)을 확인하며 active scan과 구분합니다.
6. 비슷한 배치에서 성공·실패한 작업을 비교합니다. 조건을 하나씩 바꾼 뒤 통합의 안전한 재시도 절차를 따르세요.

어댑터 접근·프록시 기능은 공식 [HA Bluetooth 안내](https://www.home-assistant.io/integrations/bluetooth/)와 [ESPHome 프록시 설정](https://esphome.io/components/bluetooth_proxy/)을 참고하세요. 처음에는 스캔 시간·연결 한도를 기본값으로 유지합니다. 스캔 강도·재시도·timeout 증가는 공통 해결책이 아닙니다.

## 증상과 실패 단계

아래 단계명은 blesession의 공통 용어입니다. 다른 통합은 이름이 다르거나 단계 보고를 제공하지 않을 수 있습니다. 모든 세션에 모든 단계가 나타나는 것은 아니며 연결을 재사용하면 새 connect 시간이 없을 수 있습니다. `unlock`·`readout` 같은 기기별 세부 단계는 공통 단계를 구체화하며 모든 기기의 공통 작업 순서를 뜻하지 않습니다.

| 증상 / `failed_stage` | 확인할 의미 | 다음 확인 |
|---|---|---|
| 기기 핸들 없음 / `unreachable` | 적합한 수신기가 현재 기기 핸들을 제공하지 않아 연결을 시작하지 못함 | 전원·깨우기·광고 조건·거리와 해당 어댑터·프록시 가용성 |
| 연결 안 됨 또는 안정화 중 끊김 / `connect` | 발견은 가능했으나 사용 가능한 연결을 만들지 못함 | 다른 연결 점유, GATT 기능, 빈 슬롯, 모델별 페어링·본딩과 해당 경로 |
| 연결 후 프로토콜 시작 전 실패 / `session` | 서비스 발견·특성 접근·알림 구독 실패 | 정확한 모델·펌웨어와 지원 GATT 프로필, 연결 직후 끊기는지 |
| 핸드셰이크·키·잠금 해제 실패 / `auth` | 데이터 교환 전 필요한 프로토콜 시작 단계가 완료되지 않음 | 기기 모드·필수 인증 정보·정확한 응답. 모든 timeout을 잘못된 키로 단정하지 않음 |
| 데이터 교환 중단 / `transfer` | 연결 끊김·예상 응답 없음 또는 쓰기 정지 | 배터리·전원·거리·어댑터/프록시 응답·네트워크와 모델별 전송 제약 |
| 완료 확인 없음 / `finish` | 데이터를 받았을 수 있으나 최종 응답·완료가 확인되지 않음 | 재전송 전 실제 기기 결과를 확인하고 모델별 완료·복구 절차 사용 |
| 종료만 실패 / `disconnect` | 작업은 끝났으나 연결 정리에 실패했을 수 있음 | 반복 실행 전 실제 기기 상태와 다음 연결 가능 여부 확인 |
| 프록시 오프라인·여러 기기 동시 실패 | 공통 경로·네트워크 영향 가능 | 프록시 전원·Ethernet/Wi-Fi·ESPHome 연결. 로컬 어댑터는 호스트·USB·Bluetooth 확인 |

작업이 성공한 상태에서 `disconnect_error`가 별도로 기록될 수 있으므로 전송 실패를 의미하지는 않습니다. `disconnect.timed_out`은 종료 중 시도 제한 시간이 만료되어 작업이 끝났어도 반환 결과가 버려졌을 수 있음을 뜻합니다. 실제 기기 상태를 확인하세요. 종료 정리나 완료 보고 실패만으로 실제 동작 명령을 반복하지 마세요.

제공되는 경우 `session.gatt_mismatch`는 필요한 서비스·특성·속성·쓰기 크기를 이용할 수 없음을 가리킵니다. 모델·펌웨어 불일치뿐 아니라 서비스 발견·MTU 협상이 끝나지 않았을 가능성도 있습니다. `write_timeout`은 쓰기가 제한 시간 안에 반환되지 않은 경우이며 알림 timeout은 예상 응답이 오지 않은 경우입니다. 서로 다른 관찰이며 특정 원인을 입증하지는 않습니다. `connect.no_slot`은 연결 용량 소진을 시사하므로 용량을 바꾸기 전 겹친 작업·불필요한 상시 연결부터 줄입니다.

## 제공되는 진단 정보 읽기

통합이 엔티티 속성·진단 다운로드·로그로 정보를 제공할 수 있습니다. 해당 통합의 실제 경로를 따르며 공통 엔티티 이름이나 진단 버튼이 있다고 가정하지 마세요. 필드가 없다고 0·성공·단계 생략으로 해석하지 않습니다.

| 제공되는 필드 | 해석 방법 |
|---|---|
| `operation`, `success`, `skipped` | 작업과 성공 여부. 실행이 거절된 시도는 아무 작업도 하지 않아 오류 없이 `skipped`와 `success: false`가 있을 수 있음 |
| `failed_stage`, `failed_detail`, `error` | 공통 단계·모델별 세부 단계·원래 오류를 함께 읽고 오류 원문 보존 |
| `likely_cause`, `likely_cause_key` | 기기별 설명 또는 일반적인 힌트. 통합 자체 설명에는 키가 없을 수 있음. 확정 원인이 아니므로 정확한 오류·경로와 대조 |
| `attempt`, `attempts`, `retrying`, `timed_out` | 통합이 기록하는 시도 정보. 재시도된 실패와 최종 실패를 구분하며 이 필드가 재시도·timeout 설정 제공을 보장하지 않음 |
| `via`, `via_type` | 확인 가능한 경우 실제 연결에 사용한 수신기. 종류는 `proxy`·`adapter` 등이며 `via_unconfirmed`와 함께 확인 |
| `via_unconfirmed` | `true`면 실제 링크에서 확인한 경로가 아니며 가장 강한 광고를 수신한 스캐너 기반일 수 있음. 확정 연결 경로로 표현하지 않음 |
| `rssi` | 해당 수신기가 관찰한 신호이며 종단 간 연결 품질 측정은 아님. 같은 경로의 추세를 비교하고 보편적인 성공 보장 기준값으로 사용하지 않음 |
| `paths` | 현재 기기를 보는 연결 가능한 수신기 수이며 남은 연결 슬롯 수는 아님. 1이면 보이는 대체 경로가 없지만 그 자체로 장애는 아님 |
| `advertised_via` | 실제 선택된 연결 경로와 다를 때 가장 강한 광고의 스캐너. 가장 강한 광고와 연결 경로는 다를 수 있음 |
| `<stage>_s`, `reused`, `disconnect_error` | 기록한 시간·연결 재사용·종료 오류. 기록한 단계만 나타나므로 같은 종류의 작업을 비교 |

통합이 `SessionReports`를 사용하면 `last`는 가장 최근 기록한 시도, `last_failure`는 가장 최근의 최종 실패, `last_retry`는 다음 시도가 이어진 실패를 보존합니다. 나중에 성공해도 과거 슬롯은 지워지지 않습니다. 시각·작업을 함께 확인하며 현재 성공 옆의 과거 실패를 새 장애로 해석하지 마세요. 실제로 표시할 보고·시각은 통합이 정합니다. 개발 세부 사항은 [보고 계약](contract.md)에 있으며 사용자 안내를 따르는 데 개발 계약을 읽을 필요는 없습니다.

## 영향을 받은 경로 복구

전체를 한꺼번에 재시작하지 말고 관찰한 근거에 맞는 항목을 확인합니다.

1. **기기:** 안정적인 전원과 문서화된 깨우기·준비 모드를 복구합니다. 중단된 작업 후 안전한 상태인지 확인하고 펌웨어·키·인증은 모델 안내를 따릅니다. 초기화·본딩 삭제·재페어링은 필요한 상태를 잃을 수 있으므로 모델 안내가 요구할 때만 수행합니다.
2. **다른 연결 점유:** 단일 연결 모델은 경쟁 앱·게이트웨이 연결을 종료한 뒤 모델에 필요한 해제 시간을 둡니다. 자동화의 중복 명령도 중지합니다. 모든 기기가 두 번째 연결을 허용한다고 가정하지 않습니다.
3. **어댑터·프록시:** 해당 경로가 온라인이고 작업을 지원하는지 확인합니다. 로컬 어댑터는 환경에 따라 호스트 접근·USB 간섭·컨테이너/VM 전달을 HA 안내로 확인합니다. 프록시는 ESPHome 연결·로그·전원·사용하지 않는 상시 연결을 확인합니다. 계속 응답이 없으면 다른 기기에 미칠 영향을 고려해 해당 경로만 재시작합니다.
4. **프록시 네트워크:** 실제 Ethernet/Wi-Fi 경로·IP 통신·API 연결을 확인합니다. Ethernet 펌웨어는 유선 연결이 필요합니다. ESPHome 자체가 끊겼다면 API 키·포트를 확인하며 이는 BLE 기기의 인증키와 별개입니다. [HA ESPHome 등록 안내](https://www.home-assistant.io/integrations/esphome/)를 참고하세요.
5. **검증:** 통합 안내에 따라 안전한 작업 한 번으로 결과·경로를 이전 실패와 비교하고 정상 갱신 복구를 확인합니다. 쓰기를 계속 반복하거나 다른 통합의 재시도·전송 간격을 복사하지 마세요.

가까운 거리와 안정적인 전원·네트워크는 무선 문제를 구분하는 데 도움이 됩니다. 수신기를 금속함·간섭 장비에서 떨어뜨리세요. 다중 수신기·자동 경로 전환·본딩 위치·상시 연결은 설치된 통합·기기·백엔드에 달려 있으며 이 안내가 보장하지 않습니다.

## 진단 및 로그

통합의 기존 문제 해결·진단 안내부터 확인합니다. HA·통합 버전, 기기 모델·펌웨어, 어댑터/프록시 모델·리비전, 해당 시 ESPHome 버전, 경로·실패 시각·시간대를 기록합니다. 광고가 보이는지와 실제 작업 완료 여부를 구분하고 실패 구간과 가능하면 가까운 성공 시도만 수집합니다.

통합 항목에서 **디버그 로깅 활성화**를 제공하면 재현할 때 켰다가 끝나면 끕니다. 그 외에는 문서화된 logger 설정을 따르며 통합 logger는 domain을 따르는 경우가 많아도 실제 이름을 확인해야 합니다. blesession은 `blesession` 아래 logger를 사용합니다(예: `blesession.hass`, `blesession.report`). 해당 이름만 켜면 통합의 프로토콜 로그가 포함되지 않을 수 있습니다. ESPHome 기기 로그는 별개입니다. 모든 Bluetooth logger를 계속 켜 두거나 제공하지 않는 로그가 있다고 주장하지 마세요.

공유 전 Bluetooth/MAC 주소, 기기 식별자, 비공개 호스트명/IP, Wi-Fi 정보, API 암호화 키, 인증·본딩 키, 접근 토큰, 개인 측정값·이름을 제거합니다. 자동 비식별화 기능이 있어도 첨부 파일·주변 로그를 직접 확인하고 경로 비교에는 일관된 익명 이름을 사용하세요.

## 문제가 계속되는 경우

통합의 기기별 문제 해결 문서와 기존 Issues·지원 링크로 돌아갑니다. 해당 통합의 기존 제보 절차에 필요한 비식별 오류·보고·환경을 보태세요. 별도의 공통 제보를 중복 생성하거나 모든 Bluetooth 장애가 blesession 라이브러리 이슈라고 가정하지 않습니다. 실제 확인한 내용과 미검증 범위를 구분하면 유지보수자가 공통 라이브러리 문제인지 판단해 필요한 곳으로 연결할 수 있습니다.

공식 설정 출처 확인일: **2026-10-18**. 단계·보고 해석은 이 리포 코드와 [계약](contract.md)을 확인했습니다. 이번 문서 작업에서 실물 기기 검증·펌웨어 컴파일·설치는 수행하지 않았습니다.
